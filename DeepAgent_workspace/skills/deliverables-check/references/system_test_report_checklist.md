
## 二、测试概况

### 2.1 测试范围

- [ ] 是否说明测试了哪些功能模块
- [ ] 是否说明未测试的功能及原因

### 2.2 测试环境说明

- [ ] 是否说明操作系统：Windows 11 / macOS / Linux
- [ ] 是否说明浏览器：Chrome 120 / Firefox 121 / Safari 17
- [ ] 是否说明Python 版本：3.11.5
- [ ] 是否说明其他相关环境信息

### 2.3 测试结果统计

- [ ] 是否说明以表格形式展示：
    
    测试类型 | 总数 | 通过 | 失败 | 通过率
    
    示例：功能测试 | 25 | 23 | 2 | 92%

## 三、需求追溯矩阵

- [ ] 是否建立需求 - 测试用例映射，确保所有需求都被测试：

    需求编号 | 需求描述 | 优先级 | 测试用例 ID | 测试结果

- [ ]  P0/P1 功能在表中是否都有对应测试用例

## 四、缺陷清单是否完整

### 4.1 按严重程度分类

- [ ] **Critical（严重）**：系统崩溃、数据丢失、安全漏洞等致命问题
- [ ] **Major（主要）**：主要功能无法使用、重要特性缺失
- [ ] **Minor（次要）**：小问题，如界面文字错误、颜色不一致等

### 4.2 每个缺陷的信息的表述是否符合格式

- 缺陷编号和严重程度（例：DEFECT-001 [Critical]）
- 问题描述
- 复现步骤
- 预期结果
- 实际结果
- 影响范围

## 五、质量评估

### 5.1 需求覆盖情况

- [ ] 是否说明总共多少项需求
- [ ] 是否说明已测试多少项
- [ ] 是否说明覆盖率百分比
- [ ] 是否说明未测试的需求及原因

### 5.2 是否说明整体质量评价

**优秀**：所有 P0 功能通过，无 Critical/Major 缺陷

**良好**：所有 P0 功能通过，少量 Major 缺陷

**合格**：P0 功能基本通过，有部分 Major 缺陷

**不合格**：P0 功能有失败，存在 Critical 缺陷

### 5.3 是否说明发布建议

**可以通过**：所有 P0 功能测试通过，无 Critical 缺陷

**需要修复**：存在 P0 功能失败或 Critical/Major 缺陷

- [ ] 是否列出必须修复的问题清单

- [ ] 是否说明建议的修复时间估算

---

**评审重点：**

- 棕地开发时是否进行回归测试并对比本次迭代与上一版本的差异
- 通过标准（必须同时满足）
    - P0 功能测试通过率 100%
    - 无 Critical 级别缺陷
    - 核心流程端到端测试通过
    - 无阻碍发布的安全漏洞


-  不通过标准（满足任一即不通过）

    - P0 功能测试有失败

    - 存在 Critical 级别缺陷

    - 存在 3 个以上 Major 级别缺陷

    - 核心流程无法走通

**不通过反馈模板：**

```
【存在问题】

2. ...

【修改要求】
1. ...
2. ...
```
