# 产品需求阶段交付物检查指南

## 一、文档元数据（YAML Frontmatter）

- [ ] 必须包含以下字段：
  ```yaml
  ---
  title: [产品名称]-PRD
  version: x.y.z（例：1.0.0，迭代时递增，如 1.1.0）
  author: Alice/产品经理
  date: YYYY-MM-DD
  state: 评审中/已通过
  ---
  ```

## 二、正文内容结构

### 2.1 需求概述

- [ ] **原始需求**：用户原话
- [ ] **需求澄清**：消除歧义的补充说明

### 2.2 产品定义

- [ ] **用户故事**：3-5 个，使用标准格式
  
     格式："作为 [角色]，我想要 [功能] 以便 [价值]"
- [ ] **产品目标**：彼此正交、可衡量的 SMART 目标
  
     每个目标具体、可量化（例："页面加载时间 < 2 秒"而非"提升性能"）

### 2.3 技术规格

- [ ] **功能需求**：按优先级排序并编号（例：REQ-P3-001-v3）
  
    P0: MVP 核心功能（缺失则产品无法使用）
    
    P1: 重要功能（显著影响用户体验）
    
    P2: 锦上添花功能
- [ ] **非功能需求**：性能、安全、兼容性等要求
- [ ] **UI 原型**：基本布局和关键交互流程说明
- [ ] **业务逻辑模型**：用户使用流程（Mermaid 流程图，可有多个）
- [ ] **待确认问题**：需要用户澄清的模糊点
- [ ] **需求追溯矩阵**（棕地开发必需）：记录需求追溯关系
  
    包含的列：新需求 ID、需求内容、来源旧需求 ID、变更类型、状态

## 三、质量标准

- [ ] **需求表述规范**：使用"必须/应该/可以"三级措辞
  
    "必须"：P0 级需求，不做无法上线
    
    "应该"：P1 级需求，强烈建议实现
    
    "可以"：P2 级需求，有时间再实现
- [ ] **可验证性**：每个需求都有明确的验收标准
- [ ] **可视化**：包含 Mermaid 图表

---

**评审重点：**

- 产品目标是否符合 SMART 原则
- P0 功能是否都有验收标准
- 是否有未标注的模糊点（应列入"待确认问题"）
- 棕地开发时是否启用并维护需求追溯矩阵

**不通过反馈模板：**

```
【存在问题】
1. ...
2. ...

【修改要求】
1. ...
2. ...
```
