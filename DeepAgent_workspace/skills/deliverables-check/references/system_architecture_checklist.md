# 系统概要设计阶段交付物检查指南

## 一、文档元数据（YAML Frontmatter）

- [ ] 必须包含以下字段：
  ```yaml
  ---
  title: 系统概要设计名称
  author: Bob/架构师
  date: YYYY-MM-DD
  version: x.y.z（例：1.0.0，迭代时递增，如 1.1.0）
  state: 评审中/已通过
  ---
  ```

## 二、可行性分析（必须首先完成）

### 2.1 技术可行性

- [ ] **技术难点识别**：列出项目中可能存在的技术挑战
- [ ] **团队能力匹配度**：当前技术栈是否成熟
- [ ] **技术风险评估**：可能的技术风险及应对措施

### 2.2 法律合规性

- [ ] **数据隐私**：是否符合 GDPR、个人信息保护法等
- [ ] **开源协议**：使用的第三方库的开源协议是否兼容
- [ ] **行业规范**：是否符合特定行业的规范要求

### 2.3 社会可行性

- [ ] **用户接受度**：目标用户对产品的接受程度
- [ ] **伦理考量**：是否存在伦理争议

### 2.4 经济可行性

- [ ] **开发成本估算**：人力成本、时间成本
- [ ] **运维成本估算**：服务器、带宽、维护成本

## 三、技术架构（可行性分析通过后）

### 3.1 技术栈选型

- [ ] **第三方库**：是否说明选型理由和权衡考虑
- [ ] **前端**（如果有）：是否说明选型理由
- [ ] **后端**（如果有）：是否说明选型理由
- [ ] **数据库**（如果有）：是否说明选型理由

### 3.2 核心模块大致划分

- [ ] 是否按业务领域大致划分了模块
- [ ] 是否标注了 MVP 功能模块和非 MVP 功能模块
- [ ] 是否说明模块间依赖关系

### 3.3 架构决策记录

- [ ] 是否记录了关键技术决策及其理由

  示例："选择 FastAPI 而非 Flask，因为需要异步支持和自动 API 文档"

## 四、开发路线图（可选但推荐）

### 4.1 阶段划分

- [ ] 是否大致划分出多个开发阶段
  
  示例：阶段 1（P0 核心功能）、阶段 2（P1 重要功能）、阶段 3（P2 优化增强）

### 4.2 里程碑

- [ ] 是否为每个阶段设置了 1-2 个关键成果

## 五、风险与待澄清事项

- [ ] 是否列出已识别的技术风险点
- [ ] 是否给出了需要进一步澄清的事项

---

**评审重点：**
- 可行性分析是否充分（4 个维度）
- 技术选型是否有明确理由
- MVP 功能是否清晰
- 每个技术决策是否能追溯到《产品需求.md》中的需求
- 棕地开发时是否评估了原有架构并标注新增/变更的技术决策

**不通过反馈模板：**
```
【存在问题】
1. ...
2. ...

【修改要求】
1. ...
2. ...
```
