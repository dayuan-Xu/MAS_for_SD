# 系统概要设计阶段交付物检查指南

## 一、文档元数据（YAML Frontmatter）

- [ ] 必须包含以下字段：
  ```yaml
  ---
  title: 系统概要设计名称
  author: Bob/架构师
  date: YYYY-MM-DD
  version: x.y.z（例：1.0.0，迭代时递增，如 1.1.0）
  state: 评审中/已通过
  ---
  ```

## 二、可行性分析（必须首先完成）

是否包含以下几点：

- [ ] **技术可行性**：技术难点、团队能力匹配度、技术风险
- [ ] **法律可行性**：数据隐私（GDPR/个人信息保护法）、开源协议兼容性、行业规范
- [ ] **社会可行性**：用户接受度、伦理考量
- [ ] **经济可行性**：开发成本（人力/时间）、运维成本（服务器/带宽/维护）

## 三、技术架构（可行性分析通过后）

### 3.1核心模块大致划分

- [ ] 是否按业务领域大致划分了模块
- [ ] 是否标注了 MVP 功能模块和非 MVP 功能模块
- [ ] 是否说明模块间依赖关系

### 3.2 数据架构设计（可选，根据项目需要持久化存储）

若需要，则检查是否包含以下几点

- [ ] **ER 图**：使用 Mermaid erDiagram 语法
- [ ] **关键表结构**：表名、主键、核心字段、索引设计
- [ ] **ORM 选型**：SQLAlchemy / Prisma / 其他，并说明理由

### 3.3 API架构设计（可选，**若项目需要提供 API**）

若需要，则检查是否包含以下几点：

- [ ] **API 风格**：RESTful / GraphQL / gRPC，并说明选型依据
- [ ] **核心端点列表**：方法、路径、简要描述（不需要详细参数，留给 Cindy）
- [ ] **认证授权机制**：JWT / Session / OAuth2，或其他

### 3.4 技术栈选型

- [ ] **第三方库**：是否说明选型理由和权衡考虑
- [ ] **前端**（如果有）：是否说明选型理由
- [ ] **后端**（如果有）：是否说明选型理由
- [ ] **数据库**（如果有）：是否说明选型理由

### 3.5架构决策记录

- [ ] 是否记录了关键技术决策及其理由

  示例："选择 FastAPI 而非 Flask，因为需要异步支持和自动 API 文档"

## 四、风险与待澄清事项

- [ ] 是否列出已识别的技术风险点，以"风险-影响-缓解措施"三列表格给出

---

**评审重点：**
- 可行性分析是否充分（4 个维度）
- 技术选型是否有明确理由
- MVP 功能是否清晰
- 每个技术决策是否能追溯到《产品需求.md》中的需求
- 棕地开发时是否评估了原有架构并标注新增/变更的技术决策

**不通过反馈模板：**
```
【存在问题】
1. ...
2. ...

【修改要求】
1. ...
2. ...
```
