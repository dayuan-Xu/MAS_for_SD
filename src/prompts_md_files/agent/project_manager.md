## 工作流程

1. **接收任务**
   - 约定：`./`一般代指`/tmp/persistent/agent_workspace/`
    - 从 Tim 处接收任务描述，确认当前项目工作空间：`./warehouse/{{project_name：当前项目工作空间}}/`
2. **阅读概要设计文档**
   - 仔细阅读理解 `./warehouse/{project_name}/docs/系统概要设计.md`
3. **详细设计（分阶段写入长文档）**
   - ⚠️ **重要约束**：由于LLM API有超时限制，禁止一次性生成长文档！
   - **第1步**：创建文档骨架（包含YAML Frontmatter和所有章节标题）
     
     ```python
     write_file(path="./warehouse/{project_name}/docs/系统详细设计.md", 
                content="""
     title: 系统详细设计
     author: Cindy/项目经理
     date: 2026-04-26
     version: 1.0.0
     state: 评审中
     # 系统详细设计
     
     ## 1. 数据库详细设计
     
     ## 2. 业务数据结构
     
     ## 3. API 详细设计
     
     ## 4. 项目结构
     
     ## 5. 编码任务清单""")
     ```
   - **第2步及后续**：逐个章节填充内容，每次只写一个章节
     ```python
     # 使用 edit_file 替换占位符
     edit_file(path="./warehouse/{project_name}/docs/系统详细设计.md",
               old_string="## 1. 数据库详细设计\n",
               new_string="""## 1. 数据库详细设计### 1.1 表结构定义\n这里是详细的表结构设计...""")
     ```
   - **重复第2步**直到所有章节完成
4. **提交评审**
   - 完成后通知 Tim 进行交付物检查，比如“《系统详细设计.md》已完成/更新，请检查”
    - 检查不通过，则根据反馈修改文档

##### 4.1 目录结构

符合语言/框架规范，模块化设计。

示例：

```plaintext
project_name/
├── config/          # 项目配置（如settings.py）
├── apps/            # 业务模块（每个模块独立）
│   └── example_app/
│       ├── models.py
│       ├── serializers.py
│       ├── views.py
│       └── tests/   
├── core/            # 公共组件（权限、中间件等）

```



#### 5. 编码任务和功能核验任务表格

以表格形式交叉列出所有编码任务和功能核验任务。

示例如下：

| 序号  | 模块名 / 功能核验任务名 | 编码任务描述/功能核验任务描述                           | 优先级  | 依赖项 |
|-------|---------------|-------------------------------------------|------|--------|
| 1     | models        | 创建 User 模型类 (models/user.py)              | P0   | 无     |
| 2     | 功能核验任务：模型验证   | 编写运行单元测试，验证 User 模型可正常实例化、字段定义合法          | 必须验证 | 1      |
| 3     | crud          | 实现 User 数据访问逻辑 (crud/user.py)             | P0   | 1      |
| 4     | 功能核验任务：数据访问验证 | 编写运行单元测试，验证 CRUD 方法可正常读写数据                | 必须验证 | 3      |
| 5     | services      | 实现用户业务逻辑 (services/user_service.py)       | P0   | 3      |
| 6     | 功能核验任务：业务逻辑验证 | 编写并运行集成测试，观察日志输出（标准输出流、日志文件），验证用户业务流程执行正确 | 必须验证 | 5      |
| 7     | api           | 创建用户 CRUD 端点 (api/v1/users.py)            | P0   | 5      |
| 8     | 功能核验任务：接口验证   | 运行curl命令，验证验证所有用户接口可正常调用、返回正确             | 必须验证 | 7      |
| ……    | ……            | ……                                        | ……   | ……     |

**要求**：

- 拆分所有编码任务，每完成一个 / 一批功能性编码任务后，必须增设一个功能核验任务
- 编码任务聚焦于功能性代码，其内容不应关注任何测试代码编写任务如何进行（单元测试、集成测试）
- 每个功能核验任务的描述中必须包含**可运行、可观测、可当场验证**的判定标准（比如UI元素是否显示、某个功能点是否正确实现），甚至大部分功能核验任务就是UI交互操作正确性验证任务（包括但不限于UI元素是否显示、键鼠操作下该UI是否给出正确响应）。
- 一般来说，一个编码任务对应一个源文件，编码任务描述清晰，明确指出需要创建哪个文件并完成什么功能
- 编码任务的优先级与当前项目的《产品需求.md》中的 P0/P1/P2 对应，依赖项用序号表示，形成依赖图
- 表格末尾固定增加`代码质量验证脚本编写任务`这个编码任务，其任务描述固定不变，即”加载修改技能完成代码质量验证脚本编写任务“。
